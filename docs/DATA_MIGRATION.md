## 第一步：保存字段目录（已完成）

在项目根目录的本地终端执行：

```powershell
.\.venv\Scripts\python.exe scripts\probe_wrds_csmar.py
```

程序依次询问用户名、隐藏输入的密码；用户本人批准手机Duo。也可以通过
`--username` 或 `.env` 中的 `WRDS_USERNAME` 指定用户名。

- 密码不从命令行、`.env` 或聊天读取，也不保存为 `.pgpass`。
- 使用官方WRDS查询辅助功能，通过只读SQLAlchemy连接绕过客户端保存密码的交互。
- 连接失败时只显示异常类型，不打印原始连接字符串和异常细节。
- 默认只获取候选CSMAR库的表名、列名、类型和字段注释，不读取行情记录。
- 输出到已被Git忽略的 `data/state/wrds_csmar_catalog.json`，不包含用户名和密码。
- 未发现候选库不等于绝对没有订阅；需核对学校订阅，也可用 `--library` 指定
  账号实际可见的准确库名，禁止凭猜测启动下载。

有了目录后，才能确认交易表、收益/复权口径、历史状态、指数成员、市值、行业和
财报公告日映射。字段注释不足以确定单位时，仍须核对供应商数据字典。

## 第二步：直接批量下载国泰安（当前主入口）

在项目根目录执行一次：

```powershell
.\.venv\Scripts\python.exe scripts\download_csmar_bulk.py --end 2026-09-28
```

- 已完成的历史成员清单会直接复用；如果尚未完成，先自动续传历史成员名单，再进入
  WRDS用户名、隐藏密码及Duo认证。完整并验证过的历史名单才可确定最终股票范围，
  不用当前800只股票倒推历史，也不把零散名单缓存当作完整股票池。
- 覆盖2015-01-01至指定结束日的沪深300、中证500累计历史成员，并下载两条指数
  基准。实际累计股票数量会超过800，以历史名单去重结果为准。
- 只读取目录核验过的11张表和必要字段。日行情、后复权行情和复权因子按月；分红
  配股、5类财务/公告日表及指数日行情按年；公司信息按股票代码限定范围读取。
  2015-01-01至2026-09-28合计508个分区，不代表要下载245张表。
- 整轮在一个WRDS连接中顺序完成，逐分区输出行数、实际最新日期、已保存容量。
  网络或认证失效时需重新本地登录；已完成分区不需要重下。
- 每个查询绑定股票、日期和行数上限；每分区最多150,000行，超限拒绝保存截断结果。
  明确拒绝日行情重复主键、不在股票范围内的代码和越界日期。
- 保存到 `data/raw/csmar/bulk/<库名>/<表名>/<月份或年份>.parquet`，使用Zstandard
  压缩；原始金额精度、状态编码、复权字段及日期字段保留，不猜测单位。
- 每分区有包含请求签名、来源、提取时间、校验和、覆盖股票及实际日期的JSON记录。
  同一请求且校验和通过才复用；日期/股票范围变化的分区重新读取，原子替换。
  当前的 `manifest.json` 明确区分正在执行、中断和下载完成等待数据检查。
- 默认复用既有完整分区；如需获取供应商对历史记录的修订，使用 `--refresh`。
  该选项会重新读取所有分区，并不等于财报的历史版本已能用于时点回测。
- 采用进程锁防止两个批量任务同时写入同一路径；逐分区检查整个 `data/` 的10 GB
  预算以及磁盘10 GB空闲保留量，写入临时副本也计入预算。
- `trd_co` 行业信息只作当前公司元数据保存，不能冒充历史行业；财务表中的
  `declaredate` 为更正披露日，不能冒充首次公告日。
- 全部查询完成后才写完成状态。空表、覆盖不足及供应商实际最新日期单独记录，
  **下载完成不等于标准化、缺口补齐或研究验收完成**。
- 此批量入口不拉BaoStock行情。后续使用补充入口补齐必要数据并切换研究输入后，按
  `data/state/legacy_market_cleanup_plan.json` 的精确范围清理被替代的旧行情。

## 替换验收顺序

1. 核验实际订阅、库表和字段单位；选择少量股票及包含除权事件的样本日期。
2. 对比CSMAR与BaoStock不复权价、成交量、成交额、交易状态及收益口径。
3. 确认复权序列可比；不能直接拼接两个供应商的复权价格水平。
4. 财报按公告/可见日期入库，保留修订记录；不按报告期提前使用数据。
5. 按年份/月份分区、指定股票和字段增量下载，标记来源。正常缺失与供应商缺口分开。
6. 验证日期覆盖、重复主键、历史成员、单位、状态、价格连续性和来源追溯。
7. 审计、对照和回归检查通过后，再切换研究/看板路径，保留可恢复旧库。
8. 确认旧数据已完整被替代且无其他流程依赖后，才清理对应旧文件。
